给 GitHub Pages 绑定自己的域名：从仓库设置到 DNS 解析、HTTPS 全记录

把 GitHub Pages 默认的 *.github.io 换成自己的域名（根域名或子域名）的完整流程——GitHub 仓库里填自定义域名、去注册商加 A / CNAME 解析、验证生效、开启强制 HTTPS，以及 Hugo 站点的 baseURL 配套修改和 Cloudflare 代理的常见坑

2026-10-26
阅读时长: 3 分钟
loading... 次

GitHub Pages 默认给你一个 用户名.github.io 的地址，能用但不够「像自己的站」。想用 whysoso.com 这种自己的域名访问，需要在两处动手：GitHub 仓库里声明自定义域名 + 域名注册商处加 DNS 解析。本文用我刚实操的 whysoso.com → whyboystudy.github.io 为例，把每一步和踩过的坑写清楚，所有记录都能照抄。

环境假设：你已有一个能正常访问的 GitHub Pages 站点（用户页 <用户名>.github.io 或项目页），且手里有一个已注册、DNS 可管理的域名。

先想清楚：根域名还是子域名

  • 根域名（apex） whysoso.com：直接把顶级域绑上来，最简洁。需要加 4 条 A 记录。
  • 子域名 www.whysoso.com 或 blog.whysoso.com：最灵活，一条 CNAME 搞定，不影响根域干别的。
  • 两者可同时绑（根域 + www 都指向 Pages），在 GitHub 里指定一个「首选域」即可。

下文两种都给，按你买的域名和偏好选。

第一步：GitHub 仓库里填自定义域名

进你的 Pages 仓库（用户页就是 <用户名>.github.io 这个仓库）→ Settings → Pages → Custom domain，输入目标域名，比如：

  • 绑根域就填 whysoso.com
  • 绑子域就填 www.whysoso.com 或 blog.whysoso.com

点 Save。

GitHub 会自动在仓库根目录生成一个 CNAME 文件（内容就是你的域名）。这个文件别手删——它是 GitHub 识别「该仓库用自定义域」的依据；如果你用自定义发布源（如 docs/ 或别的分支）也要保证它一直在。

此时先别急着勾「Enforce HTTPS」。证书还没签发，提前强制 HTTPS 会陷入重定向循环。

第二步：去注册商加 DNS 记录

这一步是把域名「指」向 GitHub Pages 的服务器。GitHub Pages 的地址固定是下面这 4 个 IP（长期稳定，不是某个会变的机器）：

1
2
3
4

185.199.108.153
185.199.109.153
185.199.110.153
185.199.111.153

绑根域名 whysoso.com：加 4 条 A 记录，分别指向上面 4 个 IP。 绑子域名 www.whysoso.com / blog.whysoso.com：加 1 条 CNAME 记录，指向 <用户名>.github.io（本文即 whyboystudy.github.io）。

关键：DNS 记录要加在真正托管你域名 DNS 的那家。很多人域名在 A 家注册、却把 NS 指向了 B 家（Cloudflare 最常见），那记录就得在 B 家加，在 A 家加不生效。判断方法：看域名的 NS（nameserver）指向谁。本文案例 whysoso.com 注册在 Spaceship，但 NS 已指向 Cloudflare，所以记录是在 Cloudflare 加的。

方案 A：域名在 Spaceship（Spaceship 自己托管 DNS）

  1. 登录 Spaceship → Domains → 找到域名 → Manage。
  2. 进 Advanced DNS / DNS Manager（高级 DNS）。
  3. 根域加 4 条 A 记录（每条只改 Value）：
    • Type A，Host @（代表根域），Value 185.199.108.153，TTL Automatic
    • 同上，Value 依次换 185.199.109.153 / 185.199.110.153 / 185.199.111.153
  4. 子域加 1 条 CNAME：
    • Type CNAME，Host www（或 blog），Value whyboystudy.github.io，TTL Automatic
  5. 每条 Save。

方案 B：域名在 Cloudflare（或 NS 已指向 Cloudflare）

  1. 登录 Cloudflare → 选域名 → 左侧 DNS → Records。
  2. 点 Add record。
  3. 根域加 4 条 A 记录：
    • Type A，Name whysoso.com（界面显示 @），IPv4 address 185.199.108.153，TTL Auto
    • 重复三条，地址换 185.199.109.153 / 185.199.110.153 / 185.199.111.153
  4. 子域加 1 条 CNAME：
    • Type CNAME，Name www（或 blog），Target whyboystudy.github.io，TTL Auto
  5. Proxy status（代理状态）先设成 DNS only（灰云 ☁️），别用橙云。原因见下方「常见坑」。

照抄填的记录表（Cloudflare 版，本文实际用的）：

Type Name 目标 / 地址 Proxy
A whysoso.com 185.199.108.153 DNS only（灰云）
A whysoso.com 185.199.109.153 DNS only（灰云）
A whysoso.com 185.199.110.153 DNS only（灰云）
A whysoso.com 185.199.111.153 DNS only（灰云）
CNAME www whyboystudy.github.io DNS only（灰云）

第三步：验证解析生效 + 开启强制 HTTPS

DNS 改动全球生效要几分钟到几小时（TTL 内通常很快）。验证：

# 根域应返回 GitHub Pages 的 4 个 IP 之一
nslookup -type=A whysoso.com
# 子域应返回 CNAME 链到 <用户名>.github.io，并最终解析到那 4 个 IP
nslookup -type=CNAME www.whysoso.com

# macOS / Linux 也可用 dig
dig +short whysoso.com
dig +short www.whysoso.com

看到对应 IP 或 whyboystudy.github.io 就说明解析通了。本文实测 whysoso.com 直接返回全部 4 个 IP、www.whysoso.com 的 CNAME 链为 whyboystudy.github.io → 185.199.108~111.153，即生效。

回到 GitHub Settings → Pages：

  • 等「DNS check」变成绿勾（GitHub 检测到你的解析指向了它）。
  • 之后 GitHub 自动签发免费证书（几分钟到半小时）。
  • 证书就绪后，勾上 Enforce HTTPS（强制 HTTPS）。

证书没签发前别勾 Enforce HTTPS，否则会重定向循环。若长时间不签发，多半是 DNS 记录还没完全生效，或你的 Cloudflare 代理挡住了 GitHub 的证书校验（见下）。

第四步：Hugo 站点配套改 baseURL 并重新部署

如果你像我一样用 Hugo，域名换了之后 config.toml / hugo.toml 里的 baseURL 必须同步，否则站内链接、RSS、sitemap 还是 .github.io：

1
2

baseURL = "https://whysoso.com/"   # 绑根域
# 或 baseURL = "https://www.whysoso.com/"   # 绑 www

改完重新 hugo 生成并推送（GitHub Pages 通常由 push 触发 Actions 自动部署）。生成后确认站点里跳转、资源引用都走新域名。

常见坑

Cloudflare 代理（橙云）导致证书签发失败 / HTTPS 循环 GitHub Pages 的免费证书靠对 whysoso.com / www 的 HTTP 校验来签发。Cloudflare 开橙云（代理）后会把流量先过 Cloudflare，可能干扰校验，证书一直签不下来。做法：

  • 加记录时先用 DNS only（灰云），等 GitHub 证书签发成功、站点能正常开，再按需把代理开回橙云（CDN 加速）。
  • Cloudflare 的 SSL/TLS 模式设成 Full（而非 Flexible）。Flexible 下 Cloudflare 到源站走 HTTP，和 GitHub 的 HTTPS 互相重定向成死循环；Full 才正确。

根域 + www 都想用 根域 4 条 A，再加一条 www 的 CNAME → <用户名>.github.io，然后在 GitHub Pages 的 Custom domain 里把 www 设成首选域（勾选 “Enforce HTTPS” 上方那项），访问 whysoso.com 会自动跳 www（或反之，按你设的首选域）。

CNAME 文件被覆盖 有些部署流程（尤其是用自定义 Action 或第三方构建）会清掉仓库根目录的 CNAME 文件，导致自定义域丢失、跳回 .github.io。确保构建产物里保留 CNAME，或在部署步骤里重新写入。

域名还没注册就去加解析 解析记录只对「已注册且 NS 已委派」的域名有意义。域名未注册时加记录无处生效。先确认 RDAP / whois 里域名已存在（本文 whysoso.com 是当天在 Spaceship 注册、NS 指向 Cloudflare 后才配的）。

2FA 与授权（顺带一提） 如果你是用 WorkBuddy 的 GitHub 连接器来自动建 PR / 改仓库，GitHub 已强制开启两步验证（2FA），连接器走 OAuth 或 Personal Access Token 授权；连不上先查网络能否稳定访问 github.com（OAuth 要跳 github.com 再跳回，中间断一丝就授权失败）。

实战小结

本文案例的完整链路：whysoso.com 在 Spaceship 注册 → NS 指向 Cloudflare（DNS 托管在 Cloudflare）→ Cloudflare 加 4 条 A（根域）+ 1 条 CNAME（www）→ GitHub Pages 填 whysoso.com → 证书签发后 Enforce HTTPS → Hugo baseURL 改为 https://whysoso.com/ 并重新部署。核心就三句话：GitHub 里声明域名、注册商里把 DNS 指到那 4 个 IP、证书出来再强制 HTTPS。Cloudflare 用户记住「先灰云后橙云、SSL 用 Full」即可避开九成问题。
